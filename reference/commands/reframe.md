Name the frame, then break it: state the frame the current work is assuming, offer 1-2 genuinely different frames, and what each changes about the next move. Fires on "reframe?", "/reframe", "am I framing this right?", "is there a better way to think about this" — or unprompted when the user has redirected the same feature or artifact twice, or when a want arrives pre-translated into a mechanism ("add X buttons"): state the want it serves in one line before building.

## Protocol — five lines, not a ceremony

1. **The assumed frame** — one sentence: what the current approach takes as given.
2. **One or two alternative frames** — genuinely different, not variations; at least one should change what *kind* of problem this is.
3. **What each changes** — one line per frame: the next move under it.

Name your lean in half a sentence if you have one; no recommendation ceremony. If the user picks a frame, continue under it — don't re-litigate. If they pick none, the assumed frame stands, now examined, and that's a fine outcome.

This is the light sibling of /x-ray (full blind-spot scan) and the diverge-before-building rule (3+ approaches before substantive builds). Reach for /reframe when the question is only "are we solving the right thing?" — not risks, not assumptions inventory, not alternatives to execute.
